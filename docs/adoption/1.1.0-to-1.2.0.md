# Upgrade from Minco 1.1.0 to 1.2.0

Minco 1.2.0 is published as one lock-step 33-package family from immutable tag
`v1.2.0` at `48df3cc0ebb8990061b60d9383ced63532941079`. Do not mix 1.1 and
1.2 packages.

Previous published baseline: `1.1.0`

Target version: `1.2.0`

Publication status: `published`

## Additive CLI commands

`cargo minco feedback task` turns one release-bound development-ready thread
into a planned repository task and receipt. `cargo minco handover` plans a
canonical JSON handover and readable Markdown packet bound to successful
release/deployment, ProjectView, source, operational ledgers, repository truth
and matching feedback receipts. Both are read-only until an exact
`--approve-plan-digest` is supplied. Neither authorizes implementation,
deployment, promotion, release or publication.

## Feedback and receipt changes

- The server owns `FeedbackReleaseBinding`; client release/environment labels
  are overwritten.
- Task conversion independently verifies release/deployment and exact release
  manifest path, bytes and SHA-256.
- Receipt schema 2 includes mandatory current source authority.
- Task metadata is neutral; client title/priority/body remain untrusted data.
- `FeedbackThread` adds defaulted `clarifications` containing question and
  resolving message IDs. Old stored threads deserialize with an empty list,
  but downstream Rust code using exhaustive `FeedbackThread { ... }` literals
  must add `clarifications: Vec::new()` or migrate to the public constructors.
- A developer reply no longer enters clarification merely because it ends in
  `?`. Reply visibly, then explicitly transition to `needs_clarification`.
  Client reply resolves the identity; open clarification blocks readiness.
- `page_url` must be HTTP(S) scheme/authority/path only—remove query, fragment
  and user information.
- Export rejects credential-shaped content and enforces conversation bounds.

Review complete `FeedbackThread` JSON snapshots and any code that assumed
punctuation changes workflow state. The field is additive; the workflow and
validation tightening is intentional.

## Plan validation and cost JSON

Stable pairs remain `lambda_zip_arm64 + api_gateway_http_api` and
`local_native + local_tcp`. Function URLs produce
`MINCO-PLAN-INGRESS-001` (declared but unsupported); incompatible pairs use
`MINCO-PLAN-INGRESS-002`. Rejection now occurs before rendering.

Cost output represents selected deployed topology. Local parity structures no
longer add AWS SQS/Scheduler/AppSync/provisioned-concurrency rates or evidence.
Lambda HTTP API retains API Gateway plus Lambda; Function URL research has no
API Gateway charge. Plan IR fields/enums are unchanged, but serialized cost
semantics change.

## Operational evidence

New source-bound inputs are the performance policy, provider ledger, AWS
candidate ledger and deterministic validator/tests. The validator writes a
machine-readable PASS/FAIL receipt binding the exact source and every validated
input. Handover accepts operational claims only through that receipt and
rechecks its bound bytes. Generated outputs excluded narrowly to avoid cycles
are the 1.2 performance result; operational-, static-, deep-review- and
publish-validation receipts; handover JSON/Markdown; feedback receipts; and
immutable provider-qualification receipts. Policies, validators, ledgers and
documents remain inside source authority.

Handover planning verifies the checked receipt seal, exact input digests and
the evidence invariants used for its truth classifications directly in the
published Rust CLI. It does not execute repository-controlled Python.
Repository development and CI continue to generate and check the canonical
receipt through the pinned `uv run --locked` environment. The current compiled
handover verifier fails closed on positive performance `PASS`, provider
`current` or capability `supported` claims; those states require a future
compiled verifier that independently covers their full provenance and proof
schema rather than trusting a self-resealed receipt.
Default output paths are unchanged. Custom JSON/Markdown alternatives must move
under `verification/handover/` so idempotent generated packets remain outside
the source tree without creating a broad dynamic exclusion.

The validator uses an explicit effective date. `NOT RUN` performance and
missing current provider proof remain warnings; `--require-current-provider`
fails. Never commit local Mac numbers as hosted evidence or treat hosted
qualification as a production SLO. Generated references now cover `PERF-*`,
`MINCO-HANDOVER-*` and ingress diagnostics.

Feedback attachment downloads must now use a destination below
`target/minco/feedback-attachments/`. This prevents untrusted raw bytes from
becoming Cargo-active source or repository configuration; move only separately
reviewed derived content into source-controlled paths.

A provider profile may be `current` only when it references a sealed,
create-only qualification receipt under
`verification/provider-evidence-receipts/`. That receipt binds the exact
current source digest, matching profile fields, evidence artifacts and cleanup
proof; setting ledger fields to `current` without the receipt fails closed.

## Plugin and public Rust compatibility

- All package versions advance together to published 1.2.0.
- First-party distribution manifests advance their exact descriptor-matching
  core requirement from `^1.1.0` to `^1.2.0`; update custom validation that
  compares requirement text rather than only SemVer membership.
- Static plugin constructors/descriptors remain; no runtime scanning, locator
  or dynamic ABI is added.
- Domain/application dependency rules remain unchanged.
- Feedback's additive serialized field is data-compatible but source-breaking
  for exhaustive downstream Rust struct literals. The stricter workflow/URL
  contract and that required literal update are the only intentional public
  Rust/data behavior changes in this tranche.

## Migration procedure

1. Pin the complete Minco family to exact version 1.2.0.
2. Run contract check/sync and review generated output.
3. Redact captured Feedback URLs to scheme/authority/path.
4. Change clarification UX to an explicit status transition.
5. Run Feedback persistence/HTTP tests against old thread fixtures.
6. Fix invalid runtime/ingress pairs instead of relying on renderer failure.
7. Update cost-JSON consumers for selected-topology semantics.
8. Add operational validation to the authoritative local quality/release gates
   and the bounded clean-Linux compatibility check.
9. Finalize source, generate its manifest, then bind exact reviewed evidence or
   truthful `NOT RUN` to that digest.
10. Plan task/handover first; apply only a reviewed digest.

## Rollback

Pin all packages together to 1.1.0 and stop invoking additive commands.
Preserve existing thread/task/handover receipts. Rollback does not undo a
deployment, promotion, data migration or publication; those remain separate
receipt-bound operations.
