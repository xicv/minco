# Upgrade from the 0.7.0 candidate to 1.0

Source candidate: `0.7.0`

Intended stable boundary: `1.0.0`

Source freeze reviewed: 2026-08-05

This guide describes the reviewed 1.0 source boundary. Do not request 1.0 from
crates.io until an immutable tag and complete 32-package registry publication
are independently visible. Source qualification, merge, hosted CI, tag,
publication, docs.rs, application adoption and live provider proof are
separate states.

## Lock-step update

The source family contains 32 packages intended for lock-step publication
under one version. Update every exact Minco dependency and every official
plugin `core_compatibility` requirement together. Do not mix a 1.0 plugin,
adapter or runtime with a 0.7 facade/core family.

The 1.0 facade retains 28 named features. The default remains `contract`,
`http` and `default-plugins`; provider, database, release, deployment,
workbench and complete `full` surfaces remain opt-in. Review the generated
[feature reference](../reference/generated/features.md) rather than copying a
hand-maintained feature list.

## Compatibility paths

No Rust item in the candidate carries `#[deprecated]`. Two CLI aliases and one
serialized predecessor remain for deliberate migration:

| Compatibility path | Canonical 1.0 path | 1.x commitment |
|---|---|---|
| `cargo minco plugin new <id>` | `cargo minco make plugin <id>` | alias remains accepted in 1.x; new automation should use the canonical command |
| `cargo minco feedback reply --message ...` | `cargo minco feedback reply --body ...` | alias remains accepted in 1.x; generated help and new automation use `--body` |
| Plan schema 1 API-only input | Plan schema 2 explicit trigger graph | schema 1 remains accepted and can migrate only under the bounded rules in the [Plan migration guide](../deployment/plan-schema-v2-migration.md) |

Removing any of these accepted paths requires the post-1.0 compatibility
policy. An alias is not permission to change command behavior silently.

## Application review

Before changing the pinned family:

1. save `cargo minco upgrade report --json` from the reviewed 0.7 source;
2. save `cargo minco contract diff --against <reviewed-revision> --json`;
3. update all exact dependencies and selected features together;
4. rerun both reports and review every changed schema, feature, plugin and
   diagnostic boundary;
5. compile the application's actual feature subsets, not only `all-features`;
6. run domain, application, adapter, HTTP and deployment-plan tests;
7. treat database migration, provider rehearsal, deployment, promotion and
   rollback as separate approvals.

The 0.7 source already contains the intended 1.0 public shapes. Any unexplained
Rust signature, feature/default, CLI, configuration, Plan, receipt,
distribution, diagnostic or behavioral difference from the reviewed freeze is
a release blocker. See the complete
[compatibility policy](../reference/compatibility.md).

## Beta component meaning

Catalog `beta` continues to mean that provider or production evidence is
bounded and the component remains opt-in. It does not mean that a published
1.x Rust API, feature name, CLI command or serialized schema can break without
a compatible version transition. Use the
[supported matrix](../reference/supported-matrix.md) for operational limits.

## Evidence boundary

The freeze does not publish 1.0 and does not prove a live workload. Require an
immutable tag, exact registry family, docs.rs completion, hosted qualification
and the consuming application's own rollout evidence before calling an
adoption complete.
