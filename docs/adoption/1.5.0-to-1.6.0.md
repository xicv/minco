# Adopt Minco 1.6.0 from 1.5.0

Published baseline: `1.6.0`
Current workspace version: `1.6.0`
Publication status: `published`

Minco 1.6.0 is an additive lock-step release. Its exact tag, all 34 registry
records and GitHub release are independently verified.

## Upgrade checklist

1. Review the audit data classification and retention policy before enabling a
   durable ledger. Audit history can contain identifiers and change metadata.
2. Upgrade the complete Minco crate family and official descriptors together.
3. Keep authorization and semantic action construction in application use
   cases; do not infer business actions from arbitrary row diffs.
4. For SQLite or PostgreSQL, configure a physically distinct audit file or
   database and operate the bounded source-journal relay.
5. For the Orders DynamoDB profile, deploy the derived audit table and exact
   cross-table transaction permissions. Do not add a generic SQL-like adapter.
6. Exercise idempotency, conditional-write races, relay retries, privacy
   redaction, pagination and post-delete history before production use.
7. Choose an explicit hot-retention/archive policy and monitor retained bytes.

## Compatibility

Existing V1 audit ports remain available. V2 records, ledger services and the
derived DynamoDB audit plan are additive. No global database default changed,
and no runtime automatically deletes, archives or rotates audit data.

The Orders OpenAPI contract adds `GET /orders/{orderId}/audit`, guarded by
`orders.audit.read`. Its cursor is opaque and bounded to 100 actions per page.

## Storage choices

- **SQLite:** a separate file prevents unbounded history from inflating the
  operational database. Explicit segment sealing near a reviewed local limit
  (the provided initial policy is 100 MiB) is useful on finite disks.
- **PostgreSQL:** use a separate database boundary and normally partition by
  time. Arbitrary numbered databases at 50 or 100 MB make queries and recovery
  harder without improving retention semantics.
- **DynamoDB:** the Orders profile uses a separate on-demand, encrypted,
  point-in-time-recovery-protected table. It has no practical size-rotation
  requirement, but every retained byte, projection and backup remains billable.

Archival is a separate operation with a durable receipt. Enable TTL or delete a
hot segment only after the archive is verified and legal-hold policy permits it.
This release contains no provider, deployment or production proof.
