# Upgrade from 0.6.0 to the 0.7.0 candidate

Published baseline: `0.6.0`
Candidate workspace version: `0.7.0`
Candidate publication status: `unpublished`

Minco `0.7.0` is a source candidate. The stable install and registry boundary
remain `0.6.0`; do not request `0.7.0` from crates.io until independent
publication evidence exists for the complete package family.

## Lock-step dependency boundary

The candidate adds four first-publication crates:

- `minco-plugin-realtime`;
- `minco-project-view`;
- `minco-mcp`;
- `minco-workbench`.

The lock-step family therefore grows from 28 to 32 publishable packages. When
adopting the candidate from a reviewed source revision, update all exact Minco
dependencies and official plugin `core_compatibility` requirements from
`0.6.0` to `0.7.0` together. Do not combine a `0.7.0` plugin with a `0.6.0`
facade or core crate.

## Rust source migrations

`cargo-semver-checks 0.50.0` was forced to treat the pre-1.0 transition as a
hypothetical minor update. It found the following expected source breaks. The
ordinary comparison treats `0.6.0` to `0.7.0` as a major transition and does
not report them.

### AWS adapter selections and resources

External `AwsAdapterSelection` literals must add
`realtime_publication: false` unless the AppSync Events publisher is selected.
`AwsRuntimeResources` literals must add
`appsync_channel_namespace_arn: None` unless that capability is present. Both
types implement `Default`, so literals that deliberately accept future
defaults can use `..Default::default()`.

### Plan and cost records

External `DeploymentPlan` literals must add these optional fields:

```rust
static_site: None,
realtime: None,
preview: None,
```

External `RuntimeCostEstimate` literals must add `realtime: None`. Prefer
building plans through typed configuration and validating them instead of
constructing a serialized Plan by hand.

### Deployment targets

External `DeploymentTarget` literals must add the 0.7 lifecycle and optional
static-site fields:

```rust
lifecycle: DeploymentTargetLifecycle::Persistent,
preview: None,
canary: None,
static_site_certificate_arn: None,
static_site_hosted_zone_id: None,
static_site_pricing_checked_on: None,
static_site_pricing_source: None,
static_site_billing_model: None,
static_site_flat_rate_eligibility: None,
```

Equivalent omitted TOML fields retain these defaults during deserialization.
Preview, canary and static-site provider configuration remain explicit opt-in
choices.

### Static-site publishers

Implementations of `StaticSitePublisher` must rename `publish` to
`publish_manifest` and accept a verified `StaticSiteReleaseManifest` instead
of a `StaticSitePlan`. The returned `StaticSitePublication` must now bind the
release manifest digest and asset inventory and state whether invalidation
completed:

```rust
#[async_trait]
impl StaticSitePublisher for MyPublisher {
    async fn publish_manifest(
        &self,
        manifest: &StaticSiteReleaseManifest,
        repository_root: &Path,
    ) -> Result<StaticSitePublication, StaticSiteError> {
        // Upload only manifest.assets from repository_root.
        Ok(StaticSitePublication {
            url: self.public_url(),
            release_manifest_digest: manifest.digest_sha256()?,
            assets: manifest.assets.clone(),
            uploaded: manifest.assets.len(),
            removed: 0,
            invalidation_id: None,
            invalidation_completed: false,
        })
    }
}
```

The service verifies the manifest before invoking the adapter. Provider
implementations still own exact upload, removal and invalidation behavior and
must not replace the manifest with a fresh source-directory scan.

## Realtime adoption

Realtime is opt-in and intentionally ephemeral. Use it to notify an active UI
that authoritative application state may have changed; retain durable domain
events and application-owned HTTP reads as the source of truth.

- backend code publishes bounded JSON envelopes through the
  provider-neutral realtime application port;
- the browser facade subscribes only while useful, never publishes, stores no
  bearer token and runs the configured HTTP resynchronization callback after
  each initial or re-established subscription;
- the minimal AWS implementation uses AppSync Events with OIDC/JWT browser
  subscriptions and IAM-only HTTP publication;
- Plan IR exposes the AppSync endpoints, exact publish IAM and explicit
  connection-minute and 5 KiB operation cost dimensions;
- the selected implementation has no Pusher dependency and requires no NAT
  Gateway, fixed compute, schedule, provisioned concurrency, connection
  registry or application heartbeat.

Review [ADR-0031](../adrs/0031-subscriber-only-realtime.md) and the
[realtime guide](../how-to/realtime.md) before enabling the plugin.

## Local project view, MCP and workbench

The three local tooling crates are independent opt-ins and are not facade
features. They expose one bounded schema-1 `ProjectView` through a read-only
stdio MCP server or loopback-only workbench. They add no hosted service,
provider access, database mutation, shell execution or write authority.

The crates have no `0.6.0` registry baseline. Their first-publication API is
therefore qualified by current compiler, rustdoc, test, containment, redaction,
protocol and browser evidence rather than a historical semver comparison.

## Evidence boundary

Local protocol, package, Plan and SAM checks do not prove live AWS deployment,
browser runtime, cleanup, registry publication or production readiness. Those
remain separate, explicitly authorised gates.

Before adopting the future 1.0 release, continue with the
[0.7-to-1.0 guide](0.7.0-to-1.0.0.md) and the frozen
[compatibility policy](../reference/compatibility.md).
