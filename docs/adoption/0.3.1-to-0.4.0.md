# Upgrade from Minco 0.3.1 to 0.4.0

Published baseline: `0.3.1`
Target published family: `0.4.0`
MSRV: Rust `1.97.1`

Minco `0.4.0` is a coordinated pre-1.0 minor boundary. It advances public
configuration, deployment planning, database/dev lifecycle, generator, package
and deployment-controller surfaces. Upgrade the full selected Minco family
together; do not mix `0.3.1` and `0.4.0` crates.

The complete 28-package `0.4.0` family is published. Source/package
qualification, merge, tag, crates.io publication, live AWS deployment and
production promotion remain independent states; confirm the exact registry
records before replacing a dependency.

## Package family

The family grows from 24 to 28 publishable packages:

| New crate | Use it for |
|---|---|
| `minco-config` | Strict typed environments, opaque `env:`/`ssm:` secret references, redacted provenance and effective configuration digests |
| `minco-db` | Migration and classified-seed catalogs, plans, verification and receipt models |
| `minco-dev` | Deterministic local dependency/process plans and supervised development lifecycle |
| `minco-deploy-aws` | AWS target guards, CloudFormation change-set/apply evidence, hosted verification and promotion receipts |

The `minco` facade remains the normal application dependency. New lifecycle
crates are not added to its default runtime behavior implicitly.

```toml
[dependencies]
minco = { version = "0.4.0", features = ["sqlx-postgres", "aws-lambda", "plan", "release"] }
```

Update every directly selected Minco crate to `0.4.0`, regenerate the lockfile,
then capture:

```text
cargo minco upgrade report --json
cargo minco contract diff --against <reviewed-0.3.1-revision> --json
cargo tree -e normal,build
```

## Plan IR schema 2

Schema 2 makes runtime topology explicit: one HTTP API function/trigger plus
opt-in worker functions, SQS queues, DLQs, event-source mappings,
partial-batch behavior and reviewed schedules. IAM, local-service, cost and
performance projections derive from those resources.

API-only schema 1 inputs remain accepted. Compare the canonical plan and
generated SAM before moving a configuration to schema 2:

```text
cargo minco deploy plan --config <path> --output target/minco/plan.json
cargo minco deploy render-sam --config <path> --output target/minco/template.yaml
cargo minco inspect --json
```

Follow the field-by-field
[Plan IR schema 2 guide](../deployment/plan-schema-v2-migration.md). A clean
static diff does not prove runtime behavior, current price or live AWS support.

## Typed configuration

Configuration schema 1 composes application and enabled-plugin fields with
strict types, fixed precedence and opaque secret references. Unknown keys,
invalid environment classes, schema conflicts and disallowed secret providers
fail closed. JSON output never includes secret values or secret-reference
names.

```text
cargo minco config schema --json
cargo minco config check --environment local --json
cargo minco config explain <path> --environment local --json
cargo minco config diff --from local --to production --json
```

Translate environment-variable conventions into declared fields before
enabling strict checks. Review
[`configuration.md`](../reference/configuration.md); do not copy secrets into
TOML, plans, logs or receipts.

## Database migrations and seeds

Migrations and seeds are explicit release operations. Lambda startup still
does not migrate. Migration set identity, file digests, applied/pending/drift
state, lock behavior and verification are bound into schema-1 plans and
receipts.

```text
cargo minco db plan --set <id> --json
cargo minco db status --set <id> --database-url-env <NAME> --json
cargo minco db verify --set <id> --database-url-env <NAME> --json
cargo minco db migrate --set <id> --database-url-env <NAME> \
  --expected-plan-digest <sha256> --receipt target/minco/migration-receipt.json
```

Seed classes are `reference`, `demo`, `test` and `bootstrap`. Production rejects
demo/test profiles; bootstrap requires exact environment authorization.
Backfills remain migrations. Preserve the direct database URL in the named
process environment only.

## Local development

`cargo minco dev` derives a schema-1 DevPlan from the application graph. It
starts only selected dependencies and process groups, reports ordered JSON
events, and stops them together. Dry-run performs no process or container
mutation.

```text
cargo minco dev --dry-run --json
cargo minco dev
cargo minco dev --profile sqlite
```

Review port/database overrides, selected Rustack services and volume policy.
Local emulator evidence is not live-provider proof.

## Contract-aware generators and stubs

The generator family now covers module, operation, migration, seeder, worker,
adapter, test and plugin structure. Every generator supports a deterministic
dry-run and refuses existing/symlinked/ambiguous targets. Operation and test
generation requires an existing valid OpenAPI operation and creates failing
specifications, not fake business success.

```text
cargo minco --json make operation <operationId> --dry-run
cargo minco --json make migration <name> --dry-run
cargo minco --json make seeder <name> --dry-run
cargo minco --json stubs publish --dry-run
```

App-owned stubs live under `stubs/minco/`; publishing them never overwrites an
existing path. Review the supported placeholders and inventory safety boundary
in [`generators.md`](../development/generators.md).

## Contract compatibility

`cargo minco contract diff` reads the reviewed VCS revision without checking it
out and classifies bounded structural changes as `breaking`, `non_breaking` or
`uncertain`. Resolve every breaking/uncertain request and response direction
against release notes, business semantics and data migrations. It is not
semantic or operational proof.

## Package and release schemas

`cargo minco package` emits schema-1 command evidence and a release manifest
with schema version 3. The manifest binds source identity, every function
artifact, OpenAPI, Plan IR, rendered template, Cargo.lock, configuration,
migration and seed digests plus toolchain versions. Older or incomplete
manifests do not silently upgrade.

```text
cargo minco package
cargo minco release verify target/minco/release.json
```

Package refuses dirty/conflicted source, changed revisions and outputs outside
ignored `target/`. Promotion consumes the exact manifest and artifacts; it
never rebuilds.

## Deployment controller and CLI

The source through M10-T03 provides this guarded sequence:

```text
cargo minco deploy changeset --dry-run --approve-release-digest <sha256>
cargo minco deploy apply --dry-run --approve-changeset-digest <sha256>
cargo minco deploy verify --dry-run
cargo minco promote --dry-run --approve-verification-digest <sha256>
```

Change-set review, apply, hosted verification and promotion use separate
receipts and approvals. Non-dry-run commands require current account, Region,
role, environment, drift and exact-artifact evidence. Hosted verification must
prove contract, readiness, authentication, smoke and artifact identity.
Promotion changes only the guarded live routing boundary.

Dry-run reports blockers and performs no AWS/HTTP contact. Local qualification
does not authorize a live rehearsal or promotion.

## Facade and feature review

Run all three consumer shapes on the exact candidate:

```text
cargo check -p minco --no-default-features --locked
cargo check -p minco --locked
cargo check -p minco --all-features --locked
cargo test -p minco --no-default-features --locked
cargo test -p minco --locked
cargo test -p minco --all-features --locked
```

Default features remain provider-neutral. SQLx, Lambda and AWS SDKs must appear
only when selected. Re-run generated PostgreSQL/SQLite applications and test
unpacked archives for each first-publish crate.

## Deferred boundaries

`0.4.0` source preparation does not implement M10-T04 rollback/canary,
M10-T05 static-site domains, M10-T06 review-environment lifecycle, M10-T07
service/cost research, M11 documentation/plugin distribution or M12 AI
workbench/1.0 freeze. It does not provide a hosted Minco control plane.

The zero-provisioned-compute promise and residual cost model are defined in
[ADR 0025](../adrs/0025-zero-provisioned-compute-review-loop.md) and the
[AWS service doctrine](../deployment/aws-service-doctrine.md).
