# Adopting the Minco 1.12.0 candidate from 1.11.0

Published baseline: `1.11.0`

Candidate workspace version: `1.12.0`

Candidate publication status: `unpublished`

Minco 1.12.0 is an additive candidate. Continue using exact published 1.11.0
dependencies in applications until the complete candidate family is separately
qualified, tagged, published, and independently verified.

## New package boundary

The candidate adds `minco-plugin-jobs`, increasing the lock-step public family
from 36 to 37 packages. It is a first-publication candidate: the package name,
owner set, and trusted publisher are not yet claimed on crates.io.

`minco-plugin-jobs` holds provider-neutral durable typed work contracts: typed
job commands with one registered handler, a bounded closed-shape envelope whose
semantic fingerprint governs deduplication and transport integrity, dispatch
modes (inline, queued, durable), publication generations with
publication-scoped FIFO deduplication identities, fenced execution claims,
atomic retry-and-republish transitions, Scheduler occurrence ingestion, and a
profile-routed dispatcher.

## Durable jobs remain opt-in

Enable `plugin-jobs` only when the application owns its job lifecycle and
supplies explicit storage (PostgreSQL or SQLite adapters), dispatch routing,
and worker composition. The plugin is disabled by default and adds no daemon,
poller, hidden schedule, queue, or fixed compute.

Inspect the archive-visible contract before adoption:

```bash
cargo minco plugin explain jobs --json
cargo minco plugin validate
```

Delivery is at least once. The durable job row owns execution state, the
publication row owns transport intent, and the queue message is delivery
never truth: every mutation is fenced by an opaque per-claim lease identity,
retries commit their state and next publication generation in one database
transaction, and Scheduler occurrences are deduplicated on
`schedule_id + scheduled_time` so provider retries converge on one job.

## Existing Plan compatibility

Durable work is an explicit sidecar: `apply_durable_work`, `validate_durable_work`,
`render_sam_with_durable_work` and `estimate_durable_work_cost` take the
topology as a parameter. The public `DeploymentPlan`, `DeploymentConfig` and
`RuntimeCostEstimate` shapes are unchanged from 1.11.0, and a disabled topology
renders zero resources and serializes identically.

## Evidence boundary

This guide describes the source candidate only. Registry publication,
deployment, hosted provider behaviour, and production evidence remain separate
states recorded by the next coordinated release task.
