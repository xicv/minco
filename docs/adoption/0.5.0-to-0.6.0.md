# Upgrade from Minco 0.5.0 to 0.6.0

Published baseline: `0.6.0`
Target version: `0.6.0`
Publication status: `published`
MSRV: Rust `1.97.1`

Minco `0.6.0` is a coordinated pre-1.0 minor release. It keeps the resource
API, deployment and zero-idle behavior of `0.5.0` while adding one inspectable
distribution contract and one public conformance boundary for statically linked
plugins, adapters and runtimes. Upgrade every selected Minco crate together.

A source version, pull request, hosted check, merge, tag, package dry run and
registry publication are separate states. All 28 exact packages are now
independently visible and non-yanked on crates.io.

## Dependency update

Update exact Minco dependencies together and regenerate the lockfile:

```toml
[dependencies]
minco = "0.6.0"

[dev-dependencies]
minco-test = "0.6.0"
```

```bash
cargo update
cargo tree -e features
cargo check --all-targets --all-features --locked
```

Pre-1.0 minor versions may contain documented public-API changes. Do not mix a
`0.5.0` plugin crate with `0.6.0` core/conformance packages merely because a
local path happens to compile.

## Add an archive-visible distribution record

Every distributed plugin-style crate points from Cargo metadata to one strict,
package-root JSON file and explicitly includes it in the crate archive:

```toml
[package]
include = ["src/**", "Cargo.toml", "minco-plugin.json"]

[package.metadata.minco]
plugin = "minco-plugin.json"
```

Start with the smallest honest schema:

```json
{
  "schema": 1,
  "id": "example",
  "kind": "plugin",
  "plugin_version": "0.1.0",
  "core_compatibility": "^0.6.0",
  "stability": "experimental",
  "default_enabled": false,
  "feature": "plugin-example",
  "runtimes": ["native"],
  "retention": "none",
  "failure_policy": {
    "mode": "fail_closed",
    "description": "Example failures remain explicit."
  },
  "documentation": {
    "reference": "https://docs.rs/minco-plugin-example"
  },
  "conformance": {
    "profile": "minco-plugin-v1",
    "evidence": ["cargo test --all-features --locked"]
  }
}
```

Unknown fields and schema versions fail closed. Secret configuration fields
may declare that they are secret but cannot carry a default. Credentials and
secret values have no field in this record.

The record describes the pre-link union of supported behavior. Cargo is still
authoritative for what is downloaded, compiled and shipped; the runtime
descriptor is authoritative for the explicitly constructed instance; the
application owns enablement, provider choice and secret references.

## Validate metadata and linked behavior

Run static inspection and overlap validation from the application or plugin
workspace:

```bash
cargo minco plugin list --json
cargo minco plugin validate --json
```

`plugin list` reads Cargo/package metadata and JSON only. `plugin validate`
also compares official linked descriptors, including identity, compatibility,
dependencies, configuration, operations, health, sensitivity and the active
resource/migration subset. Neither command downloads registry packages,
executes conformance evidence labels or enables plugin code.

## Adopt the public conformance kit

Concrete plugin tests use the same public builder as official components:

```rust
use minco_test::{ConformanceStatus, PluginConformance};

let report = PluginConformance::for_package(env!("CARGO_MANIFEST_DIR"))
    .with_plugin(ExamplePlugin)
    .run();

report.assert_passed();
assert_eq!(
    report.assurance.plugin_lifecycle,
    ConformanceStatus::Passed
);
assert_eq!(
    report.assurance.provider_live,
    ConformanceStatus::NotRun
);
```

Use `.with_configuration(value)` for required settings and
`.with_supporting_plugin(plugin)` for declared graph dependencies. A
descriptor-only report can assess package/descriptor overlap but reports the
concrete lifecycle as `not_assessed`.

```bash
cargo test --all-features --locked
cargo minco plugin test --all --json
```

A pass proves the offline package contract and supplied deterministic
composition. It does not prove an application's business policy, real database
migrations, provider calls, AWS deployment or production readiness.

## CLI compatibility

The published command surface adds and strengthens `plugin list`, `plugin
validate`, `plugin test --all` and plugin scaffolding. Broader add/init/explain/
doctor/remove mutation workflows remain planned; do not automate against
commands the CLI does not expose.

Prefer bounded JSON output for tools and AI agents. Evidence strings are inert
labels and must be selected explicitly by a reviewed workflow before execution.

## Verification checklist

```bash
cargo minco plugin validate --json
cargo minco plugin test --all --json
cargo test --all-targets --all-features --locked
cargo clippy --all-targets --all-features --locked -- -D warnings
```

For a distributed crate, additionally inspect `cargo package --list` or the
downloaded `.crate` archive and confirm `minco-plugin.json` is present. Keep
package, application, provider/live and production evidence as separate
release records.

## Deferred boundaries

Version `0.6.0` does not implement the planned plugin add/init/explain/doctor/
remove workflow, generated option-level reference, full examples matrix,
rollback/canary program, static-site domain controller, AI workbench or the 1.0
compatibility freeze. It does not add runtime package discovery, dynamic
libraries, a hosted registry or a Minco control plane.
