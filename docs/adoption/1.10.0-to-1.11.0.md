# Adopting Minco 1.11.0 from 1.10.0

Published baseline: `1.10.0`

Candidate workspace version: `1.11.0`

Candidate publication status: `unpublished`

Minco 1.11.0 is an additive candidate until the exact lock-step family is
published and independently verified. Production applications should remain on
exact `1.10.0` dependencies until that registry state is confirmed.

## What changes

The new request boundary is opt-in. Add
`x-minco-request-validation: generated` only when the OpenAPI document should
generate direct semantic checks for request-reachable schemas. Contracts
without the profile keep their existing generated DTO shape and behavior.

After opting in:

1. run `cargo minco contract check` and fix every unsupported request-reachable
   assertion or unrepresentable request shape;
2. regenerate bindings with `cargo minco contract sync` rather than editing
   `// @generated` files;
3. replace JSON/query/path extraction at the operation boundary with
   `ValidatedJson`, `ValidatedQuery`, or `ValidatedPath` as appropriate;
4. call the separate generated authorization policy before the application use
   case; and
5. keep tenancy, resource ownership, stored-state checks and business
   invariants in the application layer.

Structural decoding failures remain stable `400` Problems. Decoded values that
violate generated assertions return bounded `422 validation_failed` Problems.
Configured streamed body limits and request timeouts return Minco-owned
correlated `413` and `408` Problems without rewriting application responses.

## Compatibility and rollback

The release preserves published public struct fields, constructors, serialized
Problem shapes and non-opted DTO behavior. Roll back by restoring exact 1.10.0
package versions and the prior generated bindings. If the application has
started relying on 1.11-generated validation or authorization constants, remove
those call sites before downgrading.

This change adds no database migration, AWS resource, managed request validator,
schedule, fixed compute or provider operation. Registry publication, Pages,
docs.rs, deployment and application-runtime proof remain separate states.
