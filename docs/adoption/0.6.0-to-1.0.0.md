# Upgrade from 0.6.0 to the 1.0.0 candidate

Published baseline: `0.6.0`
Candidate workspace version: `1.0.0`
Candidate publication status: `unpublished`

Minco `1.0.0` is a locally qualified source candidate. Do not request it from
crates.io until an immutable tag and the complete 32-package registry family
are independently visible. Source qualification, hosted qualification, merge,
tag, publication, documentation, deployment and application proof remain
separate states.

## Required two-stage review

The direct version jump includes both pre-1.0 compatibility boundaries. Review
and apply the guides in order even when updating the dependency family in one
change:

1. [0.6.0 to the 0.7.0 candidate](0.6.0-to-0.7.0.md) covers the added Plan,
   provider, static-site, realtime and local-tooling surfaces and the four
   first-publication packages;
2. [0.7.0 candidate to 1.0](0.7.0-to-1.0.0.md) covers the frozen public API,
   compatibility paths and post-1.0 commitments.

Do not install or deploy the intermediate unpublished `0.7.0` source merely to
perform this review. Instead, update all exact Minco dependencies and every
official plugin `core_compatibility` requirement from `0.6.0` to `1.0.0`
together, then validate the combined effects described by both guides.

## Package-family boundary

The lock-step family grows from the published 28-package `0.6.0` baseline to
32 packages. The following packages have no published `0.6.0` baseline and
therefore require first-publication evidence rather than a historical semver
comparison:

- `minco-plugin-realtime`;
- `minco-project-view`;
- `minco-mcp`;
- `minco-workbench`.

Compile the consuming application's real facade features and separately
selected local tooling. ProjectView, MCP and Workbench remain local-only,
read-only opt-ins rather than facade defaults or hosted services.

## Adoption checks

Before calling an application migrated:

1. record the reviewed Minco source revision and complete package inventory;
2. run `cargo minco upgrade report --json` and `cargo minco contract diff`
   against the application's current reviewed boundary;
3. update the complete dependency and plugin compatibility family together;
4. compile and test every feature subset the application actually uses;
5. review schema-2 Plan output, database migrations, release manifests,
   deployment receipts and rollback assessment independently;
6. require the consuming application's own provider, deployment and runtime
   evidence before making production-readiness claims.

The source candidate does not authorize a registry upload, tag, deployment,
provider mutation or production adoption.
