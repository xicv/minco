# Upgrade from 1.2.0 to 1.2.1

Published baseline: `1.2.0`

Candidate workspace version: `1.2.1`

Candidate publication status: `unpublished`

Minco 1.2.1 is a SemVer-compatible, lock-step patch for the complete
33-package family. It refreshes the eight packaged Codex and Claude skills for
the already additive 1.2 product surface and makes their release freshness a
checked source contract. It does not change application runtime behavior,
plugin selection, skill trigger semantics or mutation authority.

## What changes

- Every packaged skill now routes the relevant browser/native contract,
  verified upload, rich mail, owned local service, Signal documentation,
  topology-aware cost and release-bound evidence workflows.
- `bundle.json` contains cumulative release-feature coverage bound to exact
  changelog-section digests and current versioned documentation.
- Rust and static mutation tests fail closed when release notes, documentation,
  skill markers or feature mappings drift.
- Deterministic Codex/Claude workflow qualification has create and exact-check
  modes, and its checked-in receipt is enforced by local and hosted gates.

## Application migration

No source migration is required. After publication, update every Minco crate in
the application together:

```bash
cargo update -p minco --precise 1.2.1
cargo minco agent plan --target all --json
```

Review the returned plan, then apply only the exact current digest:

```bash
cargo minco agent sync \
  --target all \
  --expect-plan-digest <sha256> \
  --json
```

Existing user-owned skill files and `CLAUDE.md` content remain create-only or
conflict-protected under the existing ownership rules. A stale plan, symlink,
non-regular destination or unexpected byte change still fails closed.

## Plugin compatibility

Official plugin descriptors advance in lock-step to `^1.2.1` so their declared
compatibility matches the compiled descriptors and generated plan. Descriptor
schema versions, capability IDs, default selection and static-linking rules do
not change. Third-party plugins may retain `^1.2.0`, which admits compatible
1.2 patch releases, unless they intentionally require a new 1.2.1-only API.

## Evidence and rollback

The freshness receipt proves deterministic local projection and scenario
contracts only. It is not a model-quality, deployment, provider, runtime or
production receipt. Release qualification, registry publication, docs.rs and
stable documentation remain independent gates.

Rollback application dependencies and reinstall the 1.2.0 agent bundle if the
patch must be withdrawn. Do not rewrite the immutable `v1.2.0` tag or published
crate archives. The 1.2.1 candidate must not be installed from crates.io until
its exact-source publication is separately confirmed.
